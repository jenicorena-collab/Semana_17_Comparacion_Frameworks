1. El mismo endpoint en otros frameworks

Los tres fragmentos registran una transacción para un comercio que pertenece al usuario autenticado.

Spring Boot · Java

@PostMapping("/api/transacciones")
public ResponseEntity<TransaccionDto> store(
 @Valid @RequestBody NuevaTransaccion datos,
 Principal usuario) {
 Transaccion t = servicio.registrar(usuario.getName(), datos);
 return ResponseEntity.status(201).body(TransaccionDto.de(t));
}

Django REST · Python

class TransaccionViewSet(viewsets.ModelViewSet):
 serializer_class = TransaccionSerializer
 permission_classes = [IsAuthenticated]

 def perform_create(self, serializer):
  comercio = get_object_or_404(
   Comercio, pk=self.request.data['comercio_id'],
   usuario=self.request.user)
  serializer.save(comercio=comercio, estado='Iniciada')

Preguntas de análisis — respuestas propuestas

  1. ¿Cuál delega más trabajo al framework? Django REST Framework: el ViewSet, serializer y permission_classes concentran convenciones y automatizan operaciones comunes. La respuesta depende de la configuración que no aparece en el fragmento.
  2. ¿Qué ocurre si Express elimina usuarioId? Un usuario podría consultar un comercio ajeno usando su identificador. Aparece una vulnerabilidad IDOR/BOLA por falta de autorización a nivel de objeto.
  3. ¿Dónde vive la lógica de negocio en Spring? En TransaccionService, separado del controlador. El controlador coordina la petición y delega el registro.

4. Escenarios nuevos

Caso E · Sistema de citas para clínicas

Elección propuesta: ASP.NET Core. El equipo domina C# y el entorno ya utiliza Windows, Active Directory y nube Microsoft. Cambiaría si la institución exigiera un hosting no compatible o el equipo tuviera experiencia fuerte en otro stack.

Caso F · Portal educativo con panel editorial

Elección propuesta: Django + Django Admin. El equipo conoce Python y el panel administrativo acelera la publicación de contenidos. Cambiaría si la interfaz editorial necesitara flujos muy personalizados que hicieran más conveniente otra solución.

Caso G · Miles de sensores por segundo

Elección propuesta: Go para un servicio especializado de ingesta, por concurrencia y consumo contenido; también podría evaluarse Node.js según experiencia y pruebas de carga. Cambiaría según mediciones reales de memoria, latencia y volumen.

Caso H · Pago de impuestos municipales

Elección propuesta: Laravel. El desarrollador domina PHP, el hosting compartido reduce costos y el plazo de dos meses favorece reutilizar conocimientos y herramientas. Cambiaría si existiera una integración obligatoria con una plataforma incompatible.

Conclusión tecnológica

Para nuestro proyecto académico de gestión de transacciones elegimos Laravel porque el equipo ya cuenta con experiencia en PHP, permite desarrollar en un plazo corto y ofrece herramientas integradas para rutas, validación, ORM, autenticación y pruebas. Django con Django REST Framework sería preferible si el equipo dominara Python o necesitara aprovechar Django Admin para administrar contenido. En nuestro contexto, cambiar de tecnología aumentaría el tiempo de aprendizaje sin aportar una ventaja decisiva.
